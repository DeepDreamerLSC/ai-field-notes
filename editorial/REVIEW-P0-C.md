## 2. 受众 / 带走 / 核心观点 / 最强反对

- **精确受众**：维护过自建 Agent 执行层、正在纠结"要不要上开源框架"的技术负责人 / CTO / 技术型创业者。
- **看完带走的一件事**：框架的验收标准是"能删掉多少自建机制"（净删除），不是功能表长度。
- **核心观点**：外部框架必须与已有机制**竞争职责**，而不是叠在上面。迁移要过五道门（执行等价、身份恢复、失败归类、重试纪律、数据/判断权限边界），通过后真正停止旧机制，并把新引入的 adapter / 依赖记进"新增"侧，算净删除账。
- **最强反对观点**：「自建才是技术债，跟住社区生态才是正道。」
  - 视频内应对：立场不是"不用框架"，而是"框架必须赢下职责竞争"——这个 nuance 必须保留，否则视频会变成反框架的稻草人，失去 CTO 受众的尊重。
- **证据局限**：最有说服力的证据（真实删减的代码量、运维数字）不可公开，只能抽象示意并标"示例"，说服力打折——这是它排第三的次因。

## 4. 标题与 Hook

候选标题：

1. 《接完开源框架，你的代码为什么变多了？》
2. 《选 AI 框架的标准：看它能帮你删掉多少代码》

**Hook（约 8 秒）**：「新框架接上了，demo 全绿。你低头一看——代码比上周多了三千行。」（数字标"示例"）

## 5. 旁白大纲（未来成片按约 120–130 秒设计）

1. **Hook**（0–8s）。
2. **双 Harness 陷阱**（8–35s）：把新框架套在旧执行器外面，恢复、重试、日志全变成两套；每个 bug 都要查两遍。
3. **迁移五道门**（35–70s）：执行等价 / 身份恢复 / 失败归类 / 重试纪律 / 权限边界——shadow 对照、故障注入逐项验证。
4. **单一 Execution Owner**（70–90s）：同一段执行只能有一个 owner；试点只验证"可替代的部分"，不是全量切换。
5. **净删除账本**（90–115s）：左栏删掉的旧机制，右栏新增的 adapter 与依赖维护；只有右栏不吞掉左栏，这次接入才成立。验证通过后**真正删除旧模块**，而不是"先留着以防万一"。
6. **收尾**（115–125s）：接框架前只需回答一个问题——"完成后，我们删掉了什么？"

## 7. 公开安全检查

- 不使用内部代码截图、真实行数、运维数字；"三千行"等数字标"示例"。
- 不引用私有仓库 Issue/PR、迁移记录、日志。
- 不延伸到任何客户产线收益。

## 8. 工作量与风险

- 首轮（脚本大纲 + 分镜）：约 60–75 min（本文件已含初版）。
- 未来成片：信息密度高、字幕多，估 3.5–4.5 h（模板建成后）。
- 主要风险：术语门槛与完播率的张力最大——强行通俗化会失去 CTO 受众，不简化则跳出率高。这是它排第三的核心原因，也是将来要做 2 分钟版的理由。
